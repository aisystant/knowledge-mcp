## Командные репозитории (WP-5 Ф64)

После включения `GITHUB_TEAM_REPOS_ENABLED=true` и миграции `migrations/030.sql`
пользователь подключает свой GitHub через `github_connect`, затем вызывает
`connect_source` с полным именем `организация/репозиторий`. Установка GitHub App
у организации сама по себе не даёт членам команды доступ через IWE. Для каждого
запроса к командному репозиторию сервис заново проверяет разрешение пользователя
в GitHub и выдаёт краткоживущий токен только на этот репозиторий. Старые личные
источники продолжают использовать прежний путь подключения.

Чтение и запись файла идут напрямую в GitHub; список файлов строится по текущему
дереву GitHub. Поиск берёт кандидатов из личного индекса, но перед возвратом
каждого фрагмента сравнивает весь индексированный файл с актуальным ответом GitHub и проверяет, что доступ ещё
действует. После первого файла в пустом репозитории индекс наполняет push-событие
или ручная переиндексация. Отключение источника удаляет его индексные копии и
отменяет незавершённые задания. Потеря прав в GitHub закрывает выдачу содержимого
даже до очистки копий в базе.

Для личного экземпляра задайте `GITHUB_INTEGRATION_URL` (HTTPS-адрес
github-integration-service) и тот же `GITHUB_BROKER_SHARED_SECRET`, что у сервиса
авторизации. Обе службы включаются флагом только после проверки отдельными
GitHub-аккаунтами с правами чтения, записи и без доступа. Рабочие права организации
и App installation этот код не изменяет.

## SOTA: GraphRAG + Knowledge Graphs (DP.SOTA.004)

> knowledge-mcp = retrieval layer. Цель: vector + graph traversal для multi-hop reasoning.

- Текущее: pgvector для semantic search по summary
- Следующий шаг: graph traversal по typed `related:` полям из frontmatter
- pack_search = semantic view, pack_graph = graph view, pack_get = full entity view
- При индексации: извлекать typed `related:` для построения графа связей

## Personal search: границы действующего контракта

Личный экземпляр использует этот репозиторий с `wrangler.private.toml` и
`MCP_MODE=private`. Его `search` ищет по подключённым личным источникам:
keyword/vector с fallback, без публичного LLM reranking и обогащения родителями.
`source_type` в этом режиме игнорируется; фильтровать источник нужно через `source`.

Private `search` нормализует `limit` до SQL: конечные числа усечены до целого
и ограничены диапазоном 1..20, остальные значения дают 5. Это действует для
keyword, vector и обеих fallback-веток. Полный сериализованный JSON-RPC ответ
`search` и `get_document` ограничен **32000 байт UTF-8**, включая вложенный
JSON, экранирование, предупреждения, ошибки и идентификатор запроса. Слишком
большой идентификатор даёт JSON-RPC invalid request с `id:null`.

Поиск сохраняет все выбранные результаты, порядок и метаданные. Первоначальный
фрагмент содержит до 2000 единиц UTF-16 исходного текста плюс маркер; при необходимости
фрагменты сокращаются дальше, не разрывая суррогатную пару. Сокращённый результат
имеет `content_truncated:true`. Если одни метаданные не помещаются, возвращается
явная ошибка `response_too_large`: список не обрезается молча. Индексированный
результат может быть чанком. Через gateway `personal_search` применяется ещё
сокращение до 1500 единиц UTF-16 плюс маркер.

### Чтение больших личных документов

Малые вызовы без `cursor` сохраняют прежний формат: текст из индекса либо JSON
с `sha` при `include_sha:true`/заданном `ref`. Большой ответ без согласия
на страницы даёт `isError:true` и `response_too_large`, в том числе с `include_sha`;
частичный файл нельзя случайно использовать для записи. Заголовки возвращаются
полностью или с явной ошибкой размера; страницы с `format:'headings'` запрещены.

Клиенту прямого private MCP следует:

1. Передать `get_document({filename, source, cursor:'start', format:'full'})`.
   Для точного файла GitHub добавить `include_sha:true`; `ref` фиксирует версию Git.
2. Разобрать JSON в `content[0].text`, накопить поле `content` и повторять запрос
   с `next_cursor`, сохраняя filename/source/include_sha/ref.
3. Завершить только при `complete:true` и `next_cursor:null`. При
   `document_changed` отбросить накопленные страницы и начать заново.

Каждая страница содержит `read_mode`, `content_scope`, `revision`, `complete`
и `next_cursor`. Для `read_mode:'indexed'` область — `indexed_representation`:
`complete` означает всё найденное представление, которое в старом индексе может
быть лишь первым чанком. Это **не гарантия полного исходного файла**. Только
живое чтение возвращает `read_mode:'live', content_scope:'full_file'`.
Перед редактированием такого файла нужно собрать все страницы; `sha` относится
к целому файлу. Каталог и передача `cursor` через основной шлюз проверены
синтетическими HTTP-сценариями в режимах full/browser; прочие клиентские
обёртки должны сохранять `cursor`. Бюджет 32 000 байт относится к ответу
прямого backend и не гарантируется после преобразований шлюза. Эти проверки
не подтверждают обновление кешированных каталогов действующих клиентов.

Курсор содержит смещение и хеши привязки/содержимого, а не открытый user id.
Это не подпись и не средство авторизации: каждую страницу сервер заново
авторизует и выбирает цель из текущего запроса. Изменение пользователя, источника,
имени, режима или ref отклоняет продолжение; изменение содержимого требует
перезапуска. Ревизия описывает содержимое, не историю изменений (ABA не выявляется).
На каждой странице сервер заново читает полное представление и вычисляет хеш:
лимит ответа **не ограничивает объём чтения БД/GitHub, память или стоимость запросов**.
Остальные private tools и публичный контракт этим изменением не ограничиваются.
